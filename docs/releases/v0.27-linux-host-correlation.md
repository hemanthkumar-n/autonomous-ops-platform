# v0.27.0: Linux Host-Level Correlation

Date: 2026-08-14

## Why This Release Exists

Individual Linux commands are powerful, but real incidents rarely stay in one
box.

An SRE may start with "the app is slow" and need to decide whether the first
cause is:

- disk/storage
- memory or cgroup OOM
- CPU saturation
- D-state or I/O wait
- NIC, route, or DNS
- boot/kernel instability
- a systemd service failure

v0.27 adds the first host-level correlation command so AOP can look across the
existing deterministic Linux investigators and choose the most urgent domain.

## User-Facing Command

```bash
aop investigate linux host
aop investigate linux host --path /var --iface ens5
aop investigate linux host --path /var/lib/kubelet --pid 4242
aop investigate linux host --service kubelet.service
aop investigate linux host --format json
```

## What It Does

The command runs these existing workflows:

- disk/storage investigation
- memory/OOM/cgroup investigation
- CPU/load/D-state investigation
- network/NIC investigation
- boot/kernel/grubby investigation
- optional systemd service investigation

It then returns:

- one primary host diagnosis
- severity and confidence
- domain-by-domain summary
- correlated findings
- evidence gaps
- one host-level memory record

Child workflows run with persistence disabled. This prevents one host
investigation from creating many separate domain memory records.

## Why This Matters

This is the first AOP step toward a true "one source of truth for SRE" view:

```text
single host symptom
  -> collect focused domain evidence
  -> classify each domain
  -> rank the highest-risk domain
  -> explain why that domain comes first
  -> persist one host-level memory record
```

## Safety Boundary

This command is read-only.

It does not:

- restart services
- delete files
- clear cache
- remount filesystems
- repair filesystems
- change network configuration
- change kernels or bootloader settings
- alter cgroups
- execute remediation
