# v0.31.0: LLM Provider Routing

## Purpose

v0.31.0 removes an early vendor lock-in point from AOP's reasoning layer.
Before this release, the LLM client directly created the Ollama provider. That
was fine for local demos, but future enterprise agents need a clean way to use
different reasoning backends without rewriting Linux, Kubernetes, or incident
investigation logic.

## What Changed

- Added an `LLMRouter` that resolves the configured provider.
- Kept `ollama` as the default local provider.
- Added `kimi` / `moonshot` provider selection behind explicit configuration.
- Added a Kimi/Moonshot provider using the OpenAI-compatible chat completion
  shape.
- Added a client healthcheck wrapper.
- Added offline tests for provider selection and missing Kimi API key handling.

## Configuration

Default local mode:

```env
LLM_PROVIDER=ollama
OLLAMA_BASE_URL=http://localhost:11434
LLM_MODEL_NAME=qwen2.5-coder:latest
```

Optional Kimi/Moonshot mode:

```env
LLM_PROVIDER=kimi
MOONSHOT_API_KEY=<set locally>
KIMI_MODEL_NAME=kimi-k2.6
KIMI_BASE_URL=https://api.moonshot.ai/v1
```

Secrets must stay in local environment files or secret stores. They should not
be committed.

## Current Boundary

This release adds provider routing and provider code. It does not claim that
Kimi/Moonshot has been live-validated from this machine or that provider
evaluation, scoring, cost controls, or fallback routing are complete.

## Why This Matters

This is preparation for the later enterprise agent architecture:

```text
Linux/Kubernetes evidence
  -> canonical InvestigationCase
  -> provider-neutral reasoning boundary
  -> selected LLM provider
  -> confidence-aware decision
  -> human-approved next action
```

The important design principle is that Linux and Kubernetes troubleshooting
knowledge should not depend on one model vendor.
