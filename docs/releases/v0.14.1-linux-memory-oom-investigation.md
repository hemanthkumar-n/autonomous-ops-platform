# v0.14.1: Linux Memory And OOM Investigation

Date: 2026-08-08

## Why This Release Exists

Memory issues are one of the most common places where Linux, Kubernetes, and
application troubleshooting overlap.

This release turns the v0.14 memory/OOM scenario into a deterministic AOP
investigation workflow:

```text
memory evidence
  -> MemAvailable
  -> swap movement
  -> kernel OOM logs
  -> optional cgroup memory events
  -> finding, confidence, next check, and why
```

The purpose is to teach and preserve ground-truth Linux reasoning before AI
RCA is added.

## What Changed

New CLI path:

```bash
aop investigate linux memory
aop investigate linux memory --pid 4242
aop investigate linux memory --pid 4242 --format json
```

New implementation:

```text
app/agents/linux/memory_agent.py
app/orchestration/linux_memory_workflow.py
```

Expanded collection:

```text
app/tools/linux/operations.py
```

New behavior:

- collects `free -k`, `vmstat`, top memory processes, `/proc/meminfo`, and
  recent kernel OOM logs
- optionally includes cgroup memory evidence when `--pid` is provided
- classifies kernel OOM kills
- classifies cgroup OOM events
- classifies active swap pressure
- classifies low `MemAvailable`
- classifies cgroup `memory.high` pressure
- identifies insufficient evidence without inventing a cause
- persists structured Linux memory incident records with semantic fallback

## Operator Interpretation

Important distinctions preserved by this release:

- low `free` memory is not automatically an incident
- `MemAvailable` is a better starting signal than raw free memory
- swap configured is not the same as active swap pressure
- active `si` or `so` in `vmstat` means memory movement is happening now
- a cgroup OOM can happen while the host still has available memory
- kernel OOM logs are stronger evidence than a process missing from `ps`

## Safety Boundary

The memory investigator is read-only.

It does not:

- kill processes
- clear page cache
- restart services
- change cgroup limits
- tune sysctl values
- modify swap
- remediate Kubernetes resources

## What Remains Next

The next Linux investigation candidates are:

1. CPU/load investigation, especially high load with low CPU and `D` state.
2. Network/DNS investigation with route, resolver, listener, and port checks.
3. systemd restart-loop investigation.
4. Provider-neutral evidence and dashboard contracts for v0.15.

AI RCA for Linux should come after these deterministic findings and must be
grounded only in collected evidence and preserved operator memory.
