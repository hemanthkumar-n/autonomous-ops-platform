# AOP v0.42 - Autonomous Investigation Loop

## Goal

Turn the enterprise `InvestigationCase` into a bounded evidence-seeking loop that can identify what it does not know, select an approved read-only collector, merge normalized evidence, update hypothesis reasoning, re-evaluate confidence, and stop at a clearly marked RCA candidate or a safety boundary.

## Added

- bounded `EvidencePlanner` that prioritizes RCA-blocking gaps
- resource-aware evidence requests carrying cluster, namespace, pod, node, host, container, and PID context when available
- registered collector boundary with step and total-request budgets
- normalized evidence merge with support and contradiction updates
- explicit `RootCauseCandidate` contract distinct from confirmed `root_cause`
- automatic why / why-not enrichment from collector evidence
- audit events for evidence collection, unavailable collectors, collector failures, blocking, and RCA-candidate creation
- real read-only Linux memory collector adapter backed by the existing `run_linux_memory_workflow`
- dependency injection for Linux-memory workflow tests, so the adapter is testable on macOS without pretending macOS is a Linux node
- deterministic dry-run fixture with Kubernetes pod/node identity

## Investigation lifecycle

```text
InvestigationCase
      |
      v
Confidence evaluation
      |
      +-- sufficient --> RootCauseCandidate --> stop
      |
      v
Evidence gaps
      |
      v
EvidencePlanner
      |
      v
Read-only EvidenceRequest + resource identity
      |
      v
Explicitly registered collector
      |
      v
EvidenceCollectionResult
      |
      +-- EvidenceItem(s)
      +-- supporting / contradicting evidence
      +-- why / why-not
      +-- resolved gaps
      |
      v
Re-evaluate confidence
      |
      +-- insufficient --> next bounded step
      +-- candidate --> stop
```

## RCA semantics

`rca_candidate` is not the same as a confirmed root cause.

A candidate records:

- hypothesis ID and statement
- deterministic confidence
- supporting evidence IDs
- contradicting evidence IDs
- why / why-not explanation
- validation state

`root_cause` remains reserved for a later validation or human-confirmation step.

## Safety boundaries

- no arbitrary shell execution
- no planner-generated command execution outside registered collectors
- no non-read-only collector requests
- no remediation or infrastructure mutation
- no automatic fallback to guessed commands
- bounded investigation steps and total collector calls
- collector failures and missing collectors stop or degrade safely
- Linux memory adapter uses the existing read-only AOP workflow with incident persistence disabled during autonomous evidence collection
