# v0.26.0: Linux Storage, LVM, Multipath, And NFS Investigation

Date: 2026-08-14

## Why This Release Exists

Linux disk incidents are rarely just `df -h` problems.

An experienced admin checks the full path:

```text
application write failure
  -> filesystem capacity or inodes
  -> deleted-open files or rapid growth
  -> mount options and read-only remounts
  -> block-device read-only state
  -> LVM free space and thin-pool pressure
  -> multipath path loss
  -> NFS server/client trouble
  -> storage latency and D-state correlation
  -> kernel storage evidence
```

v0.26 deepens the existing `aop investigate linux disk` command so AOP can
reason across that stack without creating a confusing second storage command.

## User-Facing Command

```bash
aop investigate linux disk --path /var
aop investigate linux disk --path /data --format json
```

## What AOP Now Collects

- filesystem byte usage through `df`
- inode usage through `df -i`
- mount source, type, options, and target through `findmnt`
- block-device topology and read-only state through `lsblk`
- LVM physical-volume, volume-group, and logical-volume inventory
- multipath device/path state
- NFS mount statistics from `/proc/self/mountstats`
- block-device latency and utilization from `iostat`
- largest directories, recent large files, deleted-open files, and kernel
  storage errors

## New Deterministic Findings

- `block_device_read_only`
- `multipath_path_loss`
- `nfs_mount_risk`
- `lvm_low_free_space`
- `lvm_thin_pool_pressure`
- `storage_latency_pressure`

Existing findings remain available:

- `read_only_filesystem`
- `storage_io_errors`
- `inode_exhaustion`
- `filesystem_capacity_exhaustion`
- `deleted_open_files`
- `rapid_file_growth`
- `insufficient_evidence`

## Why This Matters

This release captures older Linux troubleshooting discipline:

- do not assume disk-full from application write errors
- do not clean files before checking deleted-open files and retention
- do not remount read-write before checking kernel and storage errors
- do not blame CPU when the real symptom is I/O wait or D-state
- do not treat NFS, SAN, LVM, and local filesystem problems as the same thing

## Safety Boundary

The investigation is read-only.

It does not run:

- `fsck`
- `mkfs`
- `mount`
- `umount`
- `lvextend`
- `lvremove`
- `pvremove`
- `multipathd`
- cleanup, resize, repair, or reboot commands
